The app's modules run in one process. Production has a network between the
server, the database, the queue, and the client. The network drops, delays, and
duplicates.

This lesson is the failure model; the next puts it into the app.

## Partial failure

A call can fail in four ways:

- **the request never arrived** — safe to retry;
- **the request arrived, the response was lost** — the write may have happened;
- **the request is still running** — a retry can duplicate it;
- **the request failed** — retry only if the error is transient.

A timeout does not tell you which one happened. That is why retries need
idempotency.

## Timeouts

Every network call needs a deadline. Without one, a slow dependency holds the
request, the thread, and the connection until the client gives up.

The deadline should be shorter than the caller's deadline. If the API has a 10
second budget, a database call with a 30 second timeout is a bug: the client is
gone before the database answers.

## Retries

Retry only transient failures:

- connection reset, timeout, 502/503/504;
- not 400/401/403/404/422; those will fail again.

Use exponential backoff with **jitter**:

<!-- transcripts: authored -->
```text
delay = min(cap, base * 2^attempt) * random(0.5..1.5)
```

Jitter prevents a fleet of clients from retrying in lockstep and creating a
thundering herd. A retry budget (for example, 10% of requests) stops a retry
storm from becoming a self-inflicted outage.

## Idempotency

A retried `POST /tasks` can create two tasks. An idempotency key makes the
second attempt return the first result:

<!-- transcripts: authored -->
```text
Idempotency-Key: 7d3f...
```

The server stores the key and the response in the same transaction as the
write. A replay returns the stored response; a different body with the same key
is a 409.

The key is generated by the client per logical operation, not per HTTP attempt.

## Ordering

Events for one task must be ordered; events for different tasks can interleave.
Partition by task id. A consumer that needs global order has one partition and
a throughput ceiling.

A retry can reorder writes: attempt A times out, attempt B succeeds, then A
arrives. An idempotency key plus a version check (`WHERE version = ?`) rejects
the stale write.

## Exactly once

Exactly-once delivery is a property of a system boundary, not a message. Kafka
transactions can make consume-process-produce exactly once inside Kafka; the
email side effect is still at-least-once unless the provider supports an
idempotency key.

The practical rule: at-least-once delivery + idempotent side effects. Say that
in the design review; do not promise magic.

## In the app

The app's retry surface:

- the API client (`reqwest`) for the TUI;
- the outbox relay publishing to Kafka/SQS;
- the notification consumer sending email;
- the server calling Postgres/Redis.

Each gets a timeout, a retry policy for transient errors, and an idempotency
key where the operation is a write.

## If something went wrong

**The retry storm takes down the dependency.** No jitter, no budget. Add both,
and a circuit breaker.

**A retry creates a duplicate.** The write is not idempotent. Add a key and
store the result atomically.

**A stale retry overwrites a newer write.** No version check. Use optimistic
concurrency (`WHERE version = ?`) and reject the loser.

**The timeout is longer than the caller's.** Align the budgets; the inner call
must finish before the outer one gives up.

**A 400 is retried forever.** The retry classifier treats every error as
transient. Retry only 429/5xx/timeouts.

**The queue grows during an outage.** The producer keeps publishing while the
consumer is down. That is the queue's job; alert on lag and scale consumers.

## Going deeper: the fallacies

The network is not reliable, latency is not zero, bandwidth is not infinite,
the topology changes, and the clock is not global. Every distributed-system
bug is one of those fallacies.

Design for the failure you can observe. A timeout, a retry budget, and an
idempotency key cover most of the small-system cases; consensus and clocks are
for the cases that need them.
