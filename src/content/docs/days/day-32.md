The JSON file is honest and easy to inspect, but it is not a database. A
partial write, two concurrent commands, or a query over ten thousand tasks all
expose the limits.

Today the app gets a real store: SQLite, through `sqlx`. The JSON store stays
for portability; the database becomes the production path.

## Add sqlx

<!-- verify: Cargo.toml at=day-32 -->
```toml title="Cargo.toml"
sqlx = { version = "0.9", features = ["runtime-tokio", "sqlite"] }
```

`runtime-tokio` connects sqlx to the runtime we already use; `sqlite` enables
the SQLite driver. `sqlx` is async by default, so the database code uses
`.await` like the async file operations.

## The schema

Create `migrations/0001_init.sql`:

<!-- verify: migrations/0001_init.sql at=day-32 -->
```sql title="migrations/0001_init.sql"
CREATE TABLE IF NOT EXISTS tasks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    status TEXT NOT NULL,
    tags TEXT NOT NULL
);
```

The id is generated by SQLite. `title` and `status` are text; `tags` is a JSON
array in a text column. That is a deliberate simplification: tags are a small
list, and the store serializes them with `serde_json`.

The migration is idempotent because of `IF NOT EXISTS`. A real migration tool
records which versions have run; the next lesson switches to `sqlx::migrate!`
for that.

## Open the database

Create `src/db.rs` with the imports and the store type:

```rust
use std::str::FromStr;

use sqlx::sqlite::{SqliteConnectOptions, SqlitePoolOptions, SqliteRow};
use sqlx::{Row, SqlitePool};

use crate::error::TodoError;
use crate::task::{Status, Task};

pub struct SqliteStore {
    pool: SqlitePool,
}
```

The methods below go inside `impl SqliteStore`:

<!-- verify: src/db.rs at=day-32 -->
```rust title="src/db.rs"
    /// Open the database, creating it and its schema if needed.
    pub async fn open(path: &str) -> Result<Self, TodoError> {
        let options = SqliteConnectOptions::from_str(path)?.create_if_missing(true);
        let pool = SqlitePoolOptions::new()
            .max_connections(5)
            .connect_with(options)
            .await?;
        let store = Self { pool };
        store.migrate().await?;
        Ok(store)
    }

    /// Apply the initial schema.
    pub async fn migrate(&self) -> Result<(), TodoError> {
        sqlx::query(include_str!("../migrations/0001_init.sql"))
            .execute(&self.pool)
            .await?;
        Ok(())
    }
```
Declare it in `src/lib.rs`:

```rust
pub mod db;
pub use db::SqliteStore;
```


`SqliteConnectOptions` parses a URL such as `sqlite:///tmp/todo.db`.
`create_if_missing(true)` makes the first run work. `SqlitePoolOptions` keeps
up to five connections; a pool reuses them instead of opening a file handle
per query.

`include_str!` embeds the SQL file in the binary, so the schema ships with the
program. The next migration lesson replaces this with a versioned runner.

## Add a task

<!-- verify: src/db.rs at=day-32 -->
```rust title="src/db.rs"
    /// Add a task and return its database id.
    pub async fn add(&self, title: &str) -> Result<u32, TodoError> {
        let task = Task::new(0, title)?;
        let result = sqlx::query("INSERT INTO tasks (title, status, tags) VALUES (?, ?, ?)")
            .bind(&task.title)
            .bind(status_name(&task.status))
            .bind(serde_json::to_string(&task.tags)?)
            .execute(&self.pool)
            .await?;
        Ok(result.last_insert_rowid() as u32)
    }
```

`Task::new(0, title)?` reuses the blank-title rule; the id is a placeholder.
The `?` placeholders are bound parameters, not string interpolation. That is
the difference between a query and an injection.

`last_insert_rowid()` returns the id SQLite generated. Casting it to `u32` is
safe while ids fit in 32 bits; a larger system would keep `i64` or use UUIDs.
We will meet UUIDs in a later lesson.

## List and find

<!-- verify: src/db.rs at=day-32 -->
```rust title="src/db.rs"
    /// List every task in id order.
    pub async fn list(&self) -> Result<Vec<Task>, TodoError> {
        let rows = sqlx::query("SELECT id, title, status, tags FROM tasks ORDER BY id")
            .fetch_all(&self.pool)
            .await?;
        rows.iter().map(row_to_task).collect()
    }

    /// Find one task by id.
    pub async fn find(&self, id: u32) -> Result<Option<Task>, TodoError> {
        let row = sqlx::query("SELECT id, title, status, tags FROM tasks WHERE id = ?")
            .bind(id)
            .fetch_optional(&self.pool)
            .await?;
        row.as_ref().map(row_to_task).transpose()
    }
```

`fetch_all` returns every row; `fetch_optional` returns `None` instead of an
error when nothing matches. The `transpose` turns
`Option<Result<Task, _>>` into `Result<Option<Task>, _>`.

`row_to_task` is the boundary from SQL rows to the domain type:

<!-- verify: src/db.rs at=day-32 -->
```rust title="src/db.rs"
fn row_to_task(row: &SqliteRow) -> Result<Task, TodoError> {
    let id: i64 = row.try_get("id")?;
    let title: String = row.try_get("title")?;
    let status: String = row.try_get("status")?;
    let tags: String = row.try_get("tags")?;

    Ok(Task {
        id: id as u32,
        title,
        status: if status == "Done" {
            Status::Done
        } else {
            Status::Pending
        },
        tags: serde_json::from_str(&tags)?,
    })
}
```

The database stores `"Done"` or `"Pending"`; the enum is rebuilt here. The
tags column is parsed back into `Vec<String>`. Keeping the conversion in one
function means the rest of the app never sees a raw row.

## Mark it done

<!-- verify: src/db.rs at=day-32 -->
```rust title="src/db.rs"
    /// Mark a task done.
    pub async fn done(&self, id: u32) -> Result<(), TodoError> {
        let result = sqlx::query("UPDATE tasks SET status = 'Done' WHERE id = ?")
            .bind(id)
            .execute(&self.pool)
            .await?;
        if result.rows_affected() == 0 {
            return Err(TodoError::NotFound(id));
        }
        Ok(())
    }
```

`rows_affected` is how an update reports "no such row". Without the check, a
missing id would look like success.

## The tests

<!-- verify: src/db.rs at=day-32 -->
```rust title="src/db.rs"
    #[tokio::test]
    async fn add_list_and_find() {
        let (_dir, store) = store().await;
        let id = store.add("buy milk").await.unwrap();

        let tasks = store.list().await.unwrap();
        assert_eq!(tasks.len(), 1);
        assert_eq!(tasks[0].title, "buy milk");
        assert_eq!(store.find(id).await.unwrap().unwrap().id, id);
    }

    #[tokio::test]
    async fn done_marks_the_task() {
        let (_dir, store) = store().await;
        let id = store.add("buy milk").await.unwrap();

        store.done(id).await.unwrap();

        assert!(store.find(id).await.unwrap().unwrap().is_done());
        assert_eq!(store.done(999).await, Err(TodoError::NotFound(999)));
    }
```

The test helper creates a temporary directory, builds a `sqlite://` URL, opens
the database, and returns the `TempDir` so it lives as long as the store:

```rust
async fn store() -> (tempfile::TempDir, SqliteStore) {
    let dir = tempfile::tempdir().unwrap();
    let url = format!("sqlite://{}", dir.path().join("todo.db").display());
    let store = SqliteStore::open(&url).await.unwrap();
    (dir, store)
}
```

Each test gets its own file.

## If something went wrong

**`unable to open database file`.** The parent directory does not exist, or
the URL is malformed. Use `sqlite:///absolute/path/todo.db` and create the
directory.

**`no such table: tasks`.** The migration did not run. `open` calls it; if you
built the store by hand, call `migrate().await?`.

**`database is locked`.** Two writers are using the same file. SQLite allows
one writer; keep transactions short or use WAL mode in a later lesson.

**`expected i64, found ...`.** SQLite integers are `i64`; cast at the boundary,
as `row_to_task` does.

**`the trait FromRow is not implemented`.** We use manual `row.try_get`, not
the derive. Check the column name spelling; `try_get` fails at runtime.

**Tags parse fails.** The column must contain JSON. A hand-edited row with
`work` instead of `["work"]` is invalid; fix the row or add a fallback.

## Going deeper: pool, connection, transaction

A `SqlitePool` is a set of reusable connections. One connection is one file
handle and one SQLite session; a pool lets concurrent readers proceed while
one writer waits. The maximum is a tuning knob: too many connections contend
for the same file lock; too few queue the app.

A transaction is a connection with `BEGIN` and `COMMIT`. We will use it for
multi-step writes; SQLite's single-writer rule makes short transactions
especially important.

SQLite is not a toy. It is a real relational database with ACID transactions,
indexes, and a query planner. It is also a single file, which makes it a good
first database and a bad fit for many writers across machines.
